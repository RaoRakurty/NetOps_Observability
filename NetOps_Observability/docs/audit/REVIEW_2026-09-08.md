## 1. Scope and method

### What was in scope

The range touches 4,460 files (+674,617 / -24,545). Most of that is not reviewable
change:

* 973 files whose entire diff is an SPDX or copyright header. Excluded.
* Vendored Go modules, generated code (sqlc output, embedded profile JSON already
  covered by its loader), lock files, `node_modules`. Excluded.
* Test files. Read as evidence about the production code, never reviewed as the
  subject.

That leaves **907 reviewable production files**. Every one was assigned to a shard.

### How it was split

46 shards, sized by risk rather than by line count. Tier A (27 shards) is the
backend code that holds tenant data, credentials, device access or a security
verdict. Tier B (12 shards) is the correlation engine and the frontend. Tier C
(7 shards) is scripts, deployment, collectors and the AI layer.

Tier A shards were reviewed **twice by independent finders**: once under a
correctness and reliability lens, once under a security and tenant-isolation lens,
with no visibility of each other's output. Tier B and C got a single combined
lens. That is 73 finders over 916 file-slots (a few files sit in two shards; one
file, `system_backup.go`, was deleted in the range and had nothing to review).

### How findings were filtered

Every candidate went through batched adversarial refutation with a
**refute-by-default** rule: a claim survives only if the refuter can read the code
at head, walk the failure path, and fail to find a guard. Refuters were told to
look for the upstream gate, the downstream sanitiser, the test that pins the
behaviour, and the reason the code might be right. 21 claims died there, several of
them plausible-looking cross-tenant leaks that turned out to be blocked by
`TenantGate` in the SPA or by an isolation test the claimant's grep missed.
Severities were re-graded during refutation; several highs were downgraded to
medium or low on reachability grounds, and one claimed critical (`showparse`
process crash) was confirmed at critical on one lens and high on the other.

### What was NOT reviewed, and why

* **Header-only changes (973 files).** Mechanical, verified by sampling.
* **The archived tracker and `docs/archive/`.** Out of scope by CLAUDE.md.
* **Runtime behaviour.** Nothing was deployed, no stack was started, the lab was
  not contacted. Findings are code-reading plus targeted local probes: a handful of
  `go test -run`, standalone Go and Node probes of copied functions, and shell
  probes of `set -e` semantics. Where a finding rests on a probe, the finding says so.
* **Migrations against a live database.** Read as SQL, cross-checked against the
  Go that consumes them. Shard A026 found the DDL sound.
* **Third-party vendor API behaviour** (Cisco Smart Bonding, Juniper Service Case
  API). Reviewed as code paths; not exercised.

## 2. The short list

Fifteen distinct defects, most severe first. Each carries a recommendation.

### C1. Device output can kill the API process (`showparse`)

**FIX NOW.**

`internal/showparse/helpers.go:287`. `valueAfter` finds the marker offset in
`strings.ToLower(line)` and then slices the **original** line with that offset.
Go's `ToLower` is not length-preserving: U+023A and U+023E each grow from 2 bytes
to 3, and an invalid UTF-8 byte becomes a 3-byte U+FFFD.

Reproduced against the real parser: `Parse(CmdPlatformUptime, DialectCiscoIOS,
"Cisco IOS Software\nR\x81\x81\x81\x81\x81\x81\x81 uptime is 1w\n")` panics with
`slice bounds out of range [33:21]`. Shorter shifts do not panic, they return the
wrong substring silently (`"RȺȺ uptime is 4 days"` yields `Uptime = "days"`).

Nothing upstream sanitises: `splitLines` only caps length, `RedactOutput` preserves
invalid bytes, and the SSH runner returns device bytes verbatim. `Parse` is called
at `internal/protocoldiag/fanout.go:345` inside a bare worker goroutine, and there
is no `recover()` anywhere in `protocoldiag` or `tac`. An unrecovered panic in a
non-handler goroutine terminates the process, taking the API, the in-process
correlation engine and alert delivery with it. A device that emits one of two code
points in its hostname does this.

Fix: every marker in the package is ASCII. Do a byte-wise ASCII case-insensitive
scan over the original string, and add `if idx+len(marker) > len(line) { return "", false }`.
Also give `iface.go:379` the `+ " x"` sentinel its twelve sibling call sites use.
Extend the adversarial test battery past ASCII.

### C2. One vendor connector instance serves every tenant, and it caches an OAuth bearer with no key

**FIX NOW, or disable the two vendor connectors until it is keyed.**

`internal/ticketing/caseconn_registry.go:192`, `caseconn_cisco.go:319`,
`caseconn_juniper.go:237`. Six findings across two shards and both lenses converge
on one root cause.

`DefaultCaseConnectorRegistry()` builds exactly one `*CiscoSmartBondingConnector`
and one `*JuniperConnector` for the process. It is called once at server start
(`protocol_diagnostics.go:1323`, `main.go:3038`), and `TACOpenersFromRegistry` only
swaps the per-tenant config resolver; the connector object itself is shared.

Both connectors cache the minted bearer in a plain struct field with no key at all.
`bearer()` and `auth()` return the cached token whenever it is unexpired, without
ever looking at `cfg.Cisco.ClientID` / `cfg.Juniper.ClientID`. Credentials are
explicitly per tenant (`caseconn_config.go` header: bring-your-own, per tenant, no
shared Correlix identity is permitted by any vendor).

Consequences, all reachable with two tenants that have completed vendor onboarding:

* Tenant B's support case, device serial, problem description and evidence bundle
  are filed at Cisco or Juniper under tenant A's OAuth identity, spending A's quota.
* `FetchCase` sends only that bearer plus a case number, so B polling a number
  reads A's case.
* The Test button lies. `JuniperConnector.Probe` runs through the same cached
  token, so a tenant that saves a wrong `client_secret` gets `ProbeOK` with the
  message "the vendor answered and accepted the stored credential", on a credential
  that was never sent.

Separately, `caseconn_cisco.go:239` and `:293` write `c.client.StagingHost` on the
shared `*cisco.Client` outside any lock, while `sbBase()` reads it in flight. That
is a data race and a cross-tenant endpoint swap between staging and production.

The package already knows the right pattern: `mailbox_auth.go:246` keys its token
cache by a digest of the credential, and documents why.

Fix: key both caches by credential identity (provider + client id + sha256 of the
secret + token URL), the way `mailboxTokenCacheKey` does. Stop mutating the shared
client: pass the staging host per call. Ship a two-tenant test asserting a second
mint for a second credential.

### C3. SSO callback signs you in to any tenant's account with a matching username

**FIX NOW.**

`oidc.go:265` (and the elevation branch at `:333`).

Per-tenant SSO realms landed in this range. `handleTenantSSO` checks the callback
URL realm, that the alias is bound to that realm, and that the signed candidate
cookie names the same realm. All three checks are about the **connection**. The
account is then resolved by bare username in a global namespace:
`users.UpsertFederated(username, ...)` refuses only local accounts, and for an
existing federated account it **ignores the tenant argument**, merges the incoming
IdP's role mapping onto it, and returns the stored user with its original
`TenantID`. `internal/users/federated_contract_test.go:79` pins exactly that
behaviour.

Attack: tenant B's own admin holds `administration:admin` in tenant B. That is
enough to `PUT /api/auth/sso/tenant-idp/b-idp` with a discovery URL and client for
an IdP they control (`handleTenantIdPPut` stamps `TenantID` from the token and
registers it in Keycloak with `trustEmail: true`). They create a user in that IdP
named `alice`, sign in at `/t/tenant-b/sso/b-idp/login`, and `mintSession` issues a
JWT whose tenant is **tenant A**, because tenant A owns the federated account
`alice`. Alice's role and `auth_source` are rewritten on the way through.
`federatedLoginBarrier` checks suspension and account policy, not tenancy.
`guardFederatedRole` blocks only platform-owner escalation in the global tenant.

The cleanest exploit path is a victim provisioned through a non-Keycloak door
(native LDAP/TACACS, or bearer JIT at `auth.go:1149`), because those write into the
same global username namespace without a Keycloak user to trigger duplicate-account
linking.

The repo's own design doc prescribes the missing half:
`docs/design/sso-saml-oidc-design-2026-08-03.md` sections 4.2 to 4.3, opaque
per-tenant usernames and "no email-based auto-linking across issuers, ever". The
per-tenant realm work shipped; the identity-namespacing work did not.

Fix tonight: in `handleSSOCallback`, after the account is resolved and before any
session is minted, refuse when the flow's realm does not reach the account's
tenant. Refuse with the same opaque `ssoFail` message so it is not an existence
oracle, and audit the refusal. Same check in `completeElevationSSO`. Then file the
namespacing work.

### H1. Every DEM experience incident id changes once per second, so the feature does not work

**FIX NOW.** `internal/dem/experience/incident.go:319` and `:394`.

`IncidentID` hashes `Window.Start`, and `Assemble` computes `Window.Start` as
`Now() - duration` on every request, formatted to RFC3339 second precision.
Production wires `Now` to live `time.Now()`. No truncation anywhere in the package.

So the id the operator was shown a second ago no longer exists. `HandleIncidentItem`
and `handlePromote` re-assemble and match by exact id, which means the incident
detail, `/evidence`, `/timeline`, `/path` and `/promote` routes 404 for any real
client. A promotion that does land inside the same second stores
`ExperienceID` under an id that can never be re-derived, so `ApplyPromotions` never
matches, the row stays `promoted: false` forever, and the next escalate raises a
**second** platform incident because the dedup key moved. Every test freezes the
clock, which is why the suite is green.

Fix: truncate the identity window to a stable bucket before hashing. Add a test
that derives at T and fetches at T+90s through a moving clock.

### H2. The assistant's security-findings tool can only ever answer "no findings"

**FIX NOW.** `internal/../secapi/list.go:39-54` with `query.go:174`.

`ListFindings` is the non-HTTP read path. It validates a caller-built `Filters` but
never defaults `Since` / `Until`, while `BuildFilters` emits the `ts` range clause
unconditionally. The only caller, `aiSecurityFindings`, builds
`Filters{Current: q.Current}` because `ai.FindingsQuery` has no time fields at all.
The rendered query is `ts` between `0001-01-01T00:00:00Z` and
`0001-01-01T00:00:00Z`, which is a legal `strict_date_optional_time` point range
that matches nothing.

An operator asking Iris "what security findings does this device have" gets an
empty list and a clean answer over a tenant with failing criticals. That is the
false clear `ErrNoSearch` was written to prevent, arriving through the other door.
Invisible to tests because the fake OpenSearch ignores the request body.

Fix: default the window inside `ListFindings` exactly as `ParseFilters` does, and
assert on the emitted body rather than on the fake's canned response.

### H3. BGP watch closes a live hijack incident when the lookup merely fails

**FIX NOW.** `internal/bgpwatch/evaluate.go:443`.

`applyIncident` treats `ClassUnknown` (we could not measure) identically to
`ClassNone` (we measured and it is fine). An RIPEstat 502 turns the next pass into
`Measured: false`, which classifies `ClassUnknown`, which dispatches
`Alert{Resolved: true, Summary: "Cleared: 193.0.0.0/21 is no longer classified
origin_change."}` on the same dedup id. PagerDuty closes the incident. The hijack is
still live and nobody is looking.

`resolveAlert` also deletes the cool-down stamp, so a flapping upstream produces
fire, false clear, fire, false clear with the 60-minute floor bypassed: up to 288
alerts a day on one prefix.

This directly contradicts the file's own header, which states that "we could not
look" is never rendered as "we looked and it is fine".

Fix: resolve only when `inc.Class == ClassNone`. On `ClassUnknown` keep the
incident and its cool-down, and if anything is emitted at all, emit a distinct "no
longer being measured" notice that is not `Resolved: true`.

### H4. BGP origin baseline is re-learned every pass, so a full hijack classifies as clean

**Honesty fix tonight, persistence work filed.** `internal/bgpwatch/classify.go:319`.

With `expected_origins` undeclared, which is the shipped default, `Classify`
derives the baseline from the **current** observation's dominant origin. `Classify`
is pure and stateless, and nothing anywhere persists a learned origin: the only
`SetPolicy` caller in the backend is the operator's PUT handler.

So when a hijacker wins the majority of vantage points, their ASN becomes the
baseline in the same pass, the tenant's own ASN falls below `MinVantages` and is
filed as a shortfall, and the verdict is `ClassNone` with the summary "Announced as
expected; RPKI clean; visibility normal." No alert, no evidence record. Only
RPKI-invalid remains as a net, and that is blind for space with no ROA.

Meanwhile `GET /policy` tells the operator the baseline is "LEARNED from the first
observation" and the UI renders a "guessed baseline" chip saying the same.

Tonight: stop the claim. Change the API note and the UI tooltip so an operator knows
that with no declared origin, detection is limited to minority-vantage divergence.
Then file the real fix: persist the first-observation baseline per (tenant, prefix)
and classify against it.

### H5. An unrecognised interface header merges one port's error counters onto another port

**FIX NOW.** `internal/showparse/iface.go:66` and `:171`.

`parseCiscoInterfaces` only resets the current record on a header whose state phrase
is in the closed `ciscoStateWord` set. Arista's "administratively down, line
protocol is down (disabled)" and NX-OS's "down (Link not connected)" are not in it,
so those headers are treated as body text. The counter assignments below are
unconditional, so the refused interface's `input errors` / `CRC` / `output errors`
overwrite the **previous** interface's, and the refused interface disappears
entirely.

Reproduced: an EOS capture with Ethernet1 up and Ethernet2 admin-down yields one
row, `Ethernet1 up/up` with `inErr=15000 crc=15000`. Those are Ethernet2's numbers.
`if-state` is not wrapped in `requiring("{if}")`, so the untargeted battery really
does collect the multi-interface capture, and that row feeds protocol-diagnostics
evidence and the TAC bundle. An RCA verdict and a vendor case can be opened against
the wrong interface. This is the exact fabrication the package header says it exists
to prevent.

Fix: make the record boundary independent of the state vocabulary. An unindented
line that splits on " is " with a single-token name flushes and clears the current
record even when the phrase is unknown, so an unrecognised interface yields no row
instead of poisoning its predecessor. Then also add the missing EOS and NX-OS
phrases.

### H6. The config diff endpoint returns private keys that the version endpoint masks

**FIX NOW.** `internal/configstore/diff.go:284`.

`renderUnified` redacts each emitted line with `RedactLine`, which applies only the
keyword-anchored single-line rules. The PEM begin/end state machine and
`isHexBlobLine` live in `Redact()` and are never applied to a diff.

Probed the rule set directly: no rule in `secretCommon`, `secretRules[Cisco]` or
`secretRules[SRLinux]` matches a bare base64 PEM body line or a Cisco
`crypto pki certificate chain` hex line. So a device that rotates its TLS or SSH key
produces a diff whose `unified` field carries both key bodies verbatim to any
same-tenant `infrastructure:read` caller, while the audit record for that read is
stamped `"redacted": true`. The same bytes read through
`GET /config/versions/{sha}` are masked.

It gets worse on the degraded path: past `maxEditDistance` the differ emits
`blockReplace`, dumping up to 4,000 lines of both configs.

The package's own tests treat this as a leak (`dialect_test.go:205` "SECRET LEAK:
PEM body survived"), and `redact.go:180` documents a previous published-PEM bug.

Fix: factor the block state machine into a stateful line redactor and drive
`renderUnified` through it. Note that redacting the finished unified body is not
sufficient, because the `+`/`-` prefixes break `isHexBlobLine` and interleaved
lines corrupt the `inPEM` state.

### H7. A capture outage deletes the device's whole configuration history

**FIX NOW.** `internal/configstore/store.go:278` with `manager.go:550` and `:471`.

`recordFailure` writes a new version row per failed attempt, keyed by a
time-derived synthetic SHA, so each attempt is a new row rather than an upsert. Every
failure path returns before `m.prune`, so nothing is pruned during the outage. Both
store backends count failure rows against the per-device `KeepVersions` budget.

So: capture account expires, 15-minute sweeps run for a month, roughly 2,900 failure
rows accumulate for one device. Credentials are fixed, one capture succeeds, and
`prune` runs with `keep=30` over a newest-first ordering. The 30 rows kept are the
new version plus 29 failure rows. All 30 previous good versions are returned in
`removed`, and the manager deletes their sealed blobs. The diff and rollback
artifact the module exists to produce is gone, and only a `pruned_total` counter
moves.

Fix: give failure rows their own small budget, skip them when counting against
`keep`, and call `m.prune` on the failure path so a long outage cannot grow the
register without limit.

### H8. A metering read concurrent with the hourly snapshot crashes the API

**FIX NOW if any deployment runs `STORE_BACKEND=file`.** `internal/metering/store.go:293`.

`collectRange` appends `r.Seal()`, which only nils `Open` on a struct copy. The
`Meters` map header is still the store's live map, and `List` releases `s.mu`
before the caller touches it. The `metering-snapshot` worker then takes the lock and
writes into that same map through `Fold`.

`GET /api/system/licence/usage` iterates and JSON-encodes those maps with the mutex
released. The Go runtime detects it and calls `throw("concurrent map read and map
write")`, which is unrecoverable: the process dies, taking every collector and the
alert receiver with it. The narrower interleaving instead serialises a torn row into
an **ed25519-signed** usage report.

`PGStore` is unaffected (it unmarshals a fresh record per row), so this is
file-backend only. No metering test starts a goroutine, so `-race` never sees it.

Fix: deep-copy the meters map in `collectRange` (or have `Fold` allocate a fresh map
per call, which also removes the partial-mutation hazard). Add a `-race` test running
`Record` and `List` concurrently.

### H9. Security findings are readable through `/api/logs/search`, which has no permission gate

**FIX NOW.** `internal/oslog/oslog.go:35`.

`IndexBase` now maps the caller-supplied signals `secfindings` and `security` onto
the `netops-secfindings-*` family. Before this hunk those signals fell to the
default base and named indices that do not exist.

`handleLogsSearch` calls `requirePerm` zero times. `logsScope` gates only the
`applogs` signal on platform ownership. So `GET /api/logs/search?signal=security`
returns the tenant's CTEM findings, severities and device names to any principal
that authenticates, including a `RoleIngest` key from the first-party RUM snippet,
which the code itself describes as a credential printed on a billboard, and whose
permission grid is `LevelNone` everywhere.

The dedicated door is gated twice: `infrastructure:read` plus
`licenceFeature(FeatureSecurityFindings)`. The router indexes findings
unconditionally, so on Community tier the paid surface answers 402 while this one
answers 200.

Scoping still holds (own tenant plus untagged), so this is a permission and licence
bypass within the tenant, not a cross-tenant leak.

Fix: refuse `secfindings` / `security` at the `logsScope` chokepoint. The comment
added at `oslog.go:39` already says the family is deliberately not part of log
search; the free-form `signal` parameter does not enforce it. Ship a test pinning
the reachable signal set.

### H10. Digital Experience alerts carry a tenant's target names to every tenant

**FIX NOW while `FEATURE_DEM` is on in the lab.** `alert_episodes.go:101`.

The new `noc-experience` rules aggregate by `(tenant, target, kind, site, app)` and
deliberately carry no `device` label. The in-API engine loads the same rules file
and evaluates them in process, so the alert is built with `DeviceID: ""` and a
summary such as "Experience target shop.acme.com (https) p95 is 812 ms, over its
declared budget".

The S17 exception added in this range stamps the owning tenant on the episode. That
does not isolate anything, because every consumer treats an empty device as
platform-global and visible to everyone: `EpisodeStore.List` short-circuits on
`ep.Resource == ""`, and the same `a.DeviceID == ""` escape appears in
`main.go:4160`, `tenancy.go:347`, `dashboard.go:81`, `graphql.go:194`,
`topology_view.go:138` and `report_scheduler.go:553`. The existing isolation test
asserts device-less rows **must** stay visible, which confirms the stamp changes
nothing.

So a read-only user of tenant B sees tenant A's id, target hostname, site name, app
name and latency numbers.

Fix: make device-less mean platform-global only when the episode has no tenant
owner, and change the shared alert visibility rule to consult `alertTenant(a)`
rather than `DeviceID` alone. Ship the isolation test alongside it.

### H11. `backup.sh` puts the custody passphrase inside the archive it protects

**FIX NOW. One line.** `scripts/backup.sh:1097`.

Line 181 reads `BACKUP_SEALED_PASSPHRASE` from `deployment/docker/.env`, and the
fail-closed refusal at line 890 tells the operator to set it there. Under cron that
is the only sensible place. Line 1097 builds `env.backup` with
`grep -v '^BACKUP_SIGN_KEY=' .env`, which strips exactly one key.

The resulting tarball therefore contains `./sealed/sealed-material.tar.gz.enc`
(that is `data/swtpm`, which deterministically re-derives the root KEK),
`./env.backup` holding the passphrase, and `./sealed/README` with the decrypt
command written out. `BACKUP_REMOTE` then ships that one file off the host. Anyone
holding it unseals every vault secret.

This falsifies the invariant asserted in three places: the README in the archive,
`restore.sh:275`, and `docs/runbooks/backup-restore.md` ("the tarball plus the .env
inside it still cannot unseal the vault").

The existing regression at `tests/test_backup_ship.py:1172` passes vacuously,
because the fixture only ever sets the passphrase in the child process environment,
never in the fixture `.env`.

Fix: `grep -v -E '^(BACKUP_SIGN_KEY|BACKUP_SEALED_PASSPHRASE)=' ...`. Give
`BACKUP_PUSH` and `BACKUP_SSH` the same treatment, since they can carry an
`sshpass -p` transport. Then make the fixture write the passphrase into `.env` so
the test actually covers the cron path.

### H12. The "redacted" support bundle carries the SMTP password and the Slack webhook

**FIX NOW. One line, plus a design change worth doing.** `scripts/support-bundle.sh:482` and `:497`.

Both redaction passes key off the same six substrings:
`PASSWORD|PASSWD|SECRET|KEY|TOKEN|DSN`. `SMTP_PASS`, `SLACK_WEBHOOK_URL`,
`SRL_GNMI_PASS`, `EOS_GNMI_PASS` and `TWILIO_ACCOUNT_SID` match none of them.

Probed the actual sed: `SMTP_PASS: hunter2` and
`SLACK_WEBHOOK_URL: https://hooks.slack.com/...` pass through untouched while
`JWT_SECRET` is masked. Pass two cannot rescue them, because its `.env` value
extraction uses the same six substrings, so those values never enter the literal
list. `docker compose config` resolves all of them into
`compose/config.redacted.yml`, which is shipped in a file the script's own header
says leaves the host "without ever carrying a secret".

Fix now: widen the pattern to
`PASS(WORD|WD|PHRASE)?|SECRET|KEY|TOKEN|DSN|CRED|WEBHOOK_URL|_SID` in both places.
Fix properly: make pass two do what its comment claims, and seed the literal list
from **every** non-empty `.env` value of eight characters or more, minus an explicit
allowlist of known-public keys (ports, image tags, profiles, limits). That is the
only form that survives the next variable nobody anticipated.

## 6. The residual risk, in one paragraph

The dangerous class in this delta is not the crashes. It is the confident wrong
answer on a surface built to be honest. BGP watch closes a live hijack incident
because a lookup failed, and cannot detect a fully propagated origin change at all
in its shipped default while the API tells the operator it learned a baseline. The
security posture, compliance and threat screens compute totals from a truncated page
or a partial OpenSearch answer and print them as facts about the estate. The
assistant's security tool asks for a zero-width time window and reports no findings.
The config differ hands out the private keys the version endpoint masks. A capture
outage deletes the device's whole configuration history. `showparse` attributes one
port's CRC storm to another. Each of those is a small code change; together they are
a systematic drift between what the platform says and what it measured, on exactly
the surfaces the 2026-09-02 outage was supposed to have hardened. Second in line,
and the only place a tenant boundary is genuinely crossed inside the product, is the
new vendor connector layer: one process-wide Cisco connector and one Juniper
connector, each caching an OAuth bearer with no key, so one customer's support case
is filed under another customer's vendor account and the Test button confirms a
credential that was never sent. Third, and cheapest to fix, are the two scripts:
`backup.sh` puts the custody passphrase in the archive it protects, and
`support-bundle.sh` ships the SMTP password and the Slack webhook in a file stamped
"redacted". Those two put real credentials in files that leave the host, and both
are a one-line pattern change tonight.
