## M. The merged design (authoritative)

### M.0 Product statement (owner's, adopted)
For every degraded digital experience Correlix shows **who is affected, which journey is
failing, exactly where the path breaks, what changed, who owns the failing seam, how confident
we are, what evidence supports it, what action is safe, and whether the action restored the
experience.** The dashboard is a presentation layer over a **Digital Experience Causality
Platform**; Correlix navigates evidence so the customer does not navigate telemetry.

### M.1 Five layers → Correlix subsystems (best of both)
| Layer (owner) | Customer question | Correlix implementation (Correlix half + existing engine) |
|---|---|---|
| Experience | Are users succeeding? | Published, decomposable score with the **not-measured gate** (§2), SLO/error-budget framing, cohorts (site × ISP × device × version) instead of averages |
| Journey | Which workflow fails? | `JourneyDefinition` (branching, loops, abandonment) + `JourneyObservation` from **synthetic runs first**, first-party RUM second (Tier 4), sessions as context |
| Path | Where does it degrade? | The **frozen Service Path Graph contract** (`Endpoint`/`PathDefinition`/`PathObservation`/`PathHop`, ordered spine, observed ≠ inferred) rendered as the seam ribbon device → radio → LAN → egress → WAN/SASE → ISP → DNS/CDN → cloud edge → app tiers; **red mid-path = seam owner, red at target = application owner** |
| Causality | Why, what changed, who owns it? | The existing correlation engine: modality-independence verdicts (`undetermined → suspected → confirmed` needs two independent modality classes), evidence plane, seams, blast radius; DEM adds the **experience evidence class**, `ChangeEvent`, and negative evidence as first-class |
| Action | What is safe, did it work? | Existing Action Queue + RCA Verify panel + TAC escalation + ITSM connectors; recovery marked only when synthetic + RUM + path evidence agree |

### M.2 One incident, not a DEM silo (decision)
`ExperienceIncident` is **not a new store**. It is the existing `internal/incident.Incident`
with `source_type: "experience"` plus a DEM evidence packet (`impact`, `journeys`, `cohorts`,
`business_impact`, `leading_hypothesis`, `path_observation_id`, `changes`, `evidence`,
`owner/seam`, `actions`, `verification`) persisted alongside it (PG, RLS) and the correlation
object it was promoted from. `CausalHypothesis` = the correlation engine's hypotheses with the
owner's state machine `CANDIDATE → SUSPECTED → SUPPORTED → CONFIRMED / REJECTED` mapped onto
the verdict tiers (CONFIRMED requires the independence rule; SUPPORTED = suspected with ≥1
corroboration; REJECTED = contradicted). `EvidenceItem` = the evidence plane's item with the
owner's fields added: `supports/contradicts hypothesis ids`, `reliability`, `freshness`,
`independence_group` (= modality class), `provenance`, `data_class`. **Missing telemetry is
data**: `missing_evidence[]` lowers confidence and blocks CONFIRMED.

| Object | Home | Note |
|---|---|---|
| `ExperienceEvent`, `ExperienceSession` | new `internal/dem/experience` + ClickHouse table via the existing Kafka→router→ClickHouse lane (`netops.experience`) | actor_type HUMAN/SYNTHETIC/API_CLIENT/AI_AGENT; agent fields reserved (Phase N) |
| `JourneyDefinition`, `JourneyObservation` | `internal/dem` (PG, RLS) + CH observations | branching graph, SLO targets, business importance |

| `ChangeEvent` | new `internal/dem/change` normalizer over config capture/drift, cloud changes, BGP route changes, deployments/flags via `POST /api/dem/changes` | types per owner list |
| `BusinessEvent` | `POST /api/dem/business-events` → CH | extensible `business_event_type` |

Every object carries provenance (source, source object id, observed_at, event ts, data_class,
observed/inferred, confidence, freshness, schema version) and schemas are **versioned**
(`schema.name/version` + `external_schema/version`; OTel is adapted, never the storage contract).

### M.4 Score (merged)
Decomposable and versioned (owner) **and** gated/banded (Correlix): dimensions `journey_success`,
`availability`, `responsiveness`, `error_free_interaction`, `network_quality`, `user_friction`
with weights per application class in `dem/score-policy.yaml` (versioned; the policy version is
stored with every score observation). A dimension that is **not measured contributes nothing
and its weight is redistributed**; below the evidence minimum the score is **not rendered**
("not measured — reason"), never 0/100. Bands Good ≥ 70 / Fair 31–69 / Poor ≤ 30. Worst-of for
triage, p95-of for reporting, and the UI says which. Every dimension is clickable to its
evidence; "why the score fell" lists `delta_contribution` per dimension.

### M.5 Sources (Correlix ladder, owner's inputs mapped)
Tier 0 network-emitted (flow ART, SD-WAN IPFIX SLA, wireless onboarding funnel + client metrics,
Graph callRecords, DNS/DHCP/RADIUS logs, RIPEstat/CrUX) → Tier 1 existing probers → Tier 2
existing reflectors → Tier 3 one prober per site → Tier 4 first-party browser RUM snippet
(`POST /api/dem/events`) → Tier 5 desktop agent (last). Owner's additions land as producers:
OTLP/APM traces, deployments, feature flags, business events, ITSM/sentiment, AI-agent traces.
Session Replay and native mobile SDKs: **contracts only** until platform infrastructure exists.

### M.6 Navigation and screens (owner intent on the existing IA)
No IA rewrite. **Operations → Digital Experience** (`#/operations/digital-experience`) becomes
the Operations landing when `FeatureDEM` is on for the tenant; its sub-tabs are the owner's
primary nav folded in: **Experience** (overview), **Incidents** (experience-typed), **Journeys**,
**Service Paths** (existing path graph), **Synthetics** (coverage model), **Changes**,
**Data Health**. Users & Sessions, Releases, AI Investigator and Automation appear as panels
inside those tabs until their producers exist. **Experience overview** = owner's layout (SLO,
journey success, impacted users, business impact, active incidents, what changed, hotspots,
journey health, telemetry confidence) styled with the Correlix glossy grammar (heatmap, seam
ribbon, timeline scrubber, geo map). **Experience Incident** = the existing RCA workspace
extended with the owner's IA in this order: impact → timeline → experience path → hypotheses →
evidence (ALL/SUPPORTING/CONTRADICTING/MISSING) → changes (ranked by correlation, not time) →
ownership → recommended action → recovery validation. UNKNOWN and NO DATA are never healthy.

### M.7 AI Investigator = Iris, bounded
Built only after `EvidenceItem`/`CausalHypothesis` exist. Iris receives a structured evidence
packet; output validates against a JSON schema; evidence ids not in the packet are rejected;
"AI-assisted analysis based on Correlix evidence" is always shown; AI never marks CONFIRMED.
Feature-flagged (existing copilot flag + `FeatureDEM`), audited, no PII/credentials/replay DOM.

### M.8 Privacy, storage, self-observability
`data_class` on every evidence object (public/internal/customer_metadata/pseudonymous_user/pii/
regulated/credential/secret); pseudonymous user ids by default; replay refs separate; role-
controlled + audited access via the existing Sensitive-data-access module; retention by class.
Storage stays the existing stack (PG for definitions/incidents, VictoriaMetrics for series,
ClickHouse for events/observations, OpenSearch for logs); no new infrastructure without a design
note and measurement. DEM monitors itself through the pipeline debugger + `dem_*` metrics.

### M.9 Packaging (DECIDED 2026-09-05 — follows the licensing strategy of record)
The owner's licensing strategy (`docs/design/research/LICENSING_TIERING_STRATEGY_2026-09-05.md`,
TIERING_PLAN §9) puts "advanced DEM" on the **roadmap of monetizable capabilities, not in an
immediate licence gate** ("three understandable upgrade reasons, not thirty entitlements"), meters DEM
sessions/journeys/checks as a **diagnostic meter on-prem** (never money), and reserves DEM sessions as a
possible **narrow SaaS overage meter later**. Therefore: **no `FeatureDEM` entitlement** — the locked
Feature vocabulary is unchanged; DEM is gated only by the `FEATURE_DEM` deployment flag; network-side
DEM rides the **monitored-device** unit (a probed target is not a device and consumes nothing); **no RUM
unit at launch** — first-party RUM, when built, is metered diagnostically and packaged when the strategy
is revisited with usage evidence. `tenants`/`orgs`/retention ceilings apply to DEM data as to everything.

### M.10 Delivery (owner's slices on top of the shipped plumbing)
Slice 0 (done): catalogue, probers, series, score maths, alerts, grounding. **Slice 1:** repo

# Correlix half, DRAFT v0 (kept for provenance; superseded where §M differs)

**Status:** draft to be MERGED with the owner's own DEM document ("best of both"). Nothing
visual is built until the merged version is ratified. Research behind every claim:
`docs/design/research/DEM_MARKET_RESEARCH_2026-09-05.md` (19 vendors, primary sources, 60
unverified markers kept as such). Data model already in progress:
`docs/design/DEM_DATA_MODEL_2026-09-05.md` (plumbing agent).

## 0. The one-sentence product
Correlix DEM answers, for every user, site and application, **"is the experience good, and if
not, which seam owns the fix"** — from device → radio → LAN → site egress → WAN overlay/underlay
→ ISP → SaaS/DC → application tier — with sub-minute detection, an auditable published score,
and nothing installed anywhere for the first four tiers of evidence.

Why this wins: the market converged on a 0–100 score per user/app/5-min window, but **nobody
owns the seam-attributed join** (endpoint vendors stop at the NIC, path vendors stop at the SaaS
front door, APM starts there), incumbents detect in tens of minutes, and the category leader is
criticised for its unit licensing. Correlix already has the seam vocabulary, the correlation
engine, per-path p50/p99, a wireless per-client tier shaped like an SLE, flows with app-id,
STAMP/traceroute/HTTP/TCP/ICMP synthetics, BGP/RIPEstat, and honest "not measured" discipline.

## 1. Scope (owner: "user endpoints, SD-WAN, DC, enterprise LAN, all endpoint types")
| Domain | Endpoint types | Experience questions |
|---|---|---|
| **Users** | laptops/desktops (Win/macOS/Linux), phones/tablets (iOS/Android via MDM signals only), thin clients, kiosks | Can I reach and use app X at acceptable speed? Calls/video quality? |
| **Enterprise LAN / Wi-Fi** | wired clients, Wi-Fi clients, printers, cameras, IoT/OT, badge readers | Onboarding funnel (assoc → auth → DHCP → DNS), radio health, roaming, wired errors |
| **SD-WAN / branch** | branch routers/edges, tunnels, DIA/MPLS underlays, on-ramps to SASE | Per-app SLA per tunnel/site (loss/latency/jitter), overlay vs underlay fault, ISP blackout/brownout |
| **DC / cloud** | servers, VMs, containers, load balancers, fabrics, cloud VPC paths | Reachability and latency to app tiers, fabric path stability, east-west vs north-south |
| **SaaS / Internet** | M365, Teams/Zoom, Salesforce, ServiceNow, DNS/CDN | Front-door reachability, TLS/HTTP timing, BGP/path changes |

## 2. Score (published, auditable)
- **Shape:** 0–100, three bands, boundaries fixed and never inverted: Good ≥ 70, Fair 31–69,
  Poor ≤ 30 (Palo Alto/Netskope-class boundaries). The formula is documented in the product
  and on every score tooltip ("how this number was made").
- **Per observer, then per subject:** every measurement is `(value, source, observer, tier,
  confidence)`. An application legitimately has one score per observer (synthetic from site A,
  flow-derived from site B, RUM from the browser); the subject score is the **worst-of** for
  triage and the **p95-of** for reporting, and the UI always says which one is on screen.
- **Availability is a gate, not a term:** below the minimum evidence (fewer than 2 contributing
  sources over the window, or no successful sample) the score is **not rendered** — "not
  measured — reason", never 0 and never 100.
- **Components:** availability (success ratio vs budget), responsiveness (latency/TTFB/RTT vs
  budget, p50 and p95), quality (loss/jitter/MOS for real-time; LCP/INP/CLS for web), stability
  (path/hop changes, roams, re-auths). Weights per application class (web, real-time, thick
  client, infrastructure) are data (`dem/classes.yaml`), reviewed like skills.
- **Baselines (three tiers):** self (per subject, from Correlix's own p50/p99 history), cohort
  (site × ISP ASN × on-ramp, ≥ 20 members before it is used; worst-2 %-within-cohort flags
  outliers), global (CrUX p75 for public web apps; RIPEstat + per-tenant corroboration for
  Internet events — no cross-customer corroboration is possible on-prem, and the UI says so).

## 3. Sources — the minimal-interference ladder (build in this order)
| Tier | Source | What it yields | Interference |
|---|---|---|---|
| 0 | **What the network already emits:** flow ART fields (client/server network latency, app latency, retransmits), **SD-WAN IPFIX with BFD loss/latency/jitter per tunnel** (Cisco cleanest; Versa Analytics / Fortinet / Prisma via their APIs), wireless controller **onboarding funnels + client RSSI/SNR/retries/roams**, **802.11 vendor analytics via the AP** (Apple/Intel endpoint-side signal, no agent), DHCP/DNS/RADIUS logs, **Microsoft Graph `callRecords`** (Teams call quality per user, agentless), RIPEstat, CrUX | none installed |
| 1 | Correlix's existing probers: STAMP, Paris traceroute, HTTP/TCP/ICMP/DNS synthetics, wan-echo | already running |
| 2 | Reflectors that already exist: TWAMP-Light responders on edges/firewalls, IP SLA/RPM results over SNMP (verify per vendor) | config read only |
| 3 | **One opt-in prober per site** (branch), never one per tunnel; DSCP-aware probes per app class; multiple traces per round to expose ECMP; published per-round packet/byte budget and per-tenant probe-rate ceiling | one container/VM per site |
| 4 | **Browser RUM** for apps the customer owns: a tiny snippet posting Navigation/Resource timing + Web Vitals to Correlix (no third-party) | one script tag |
| 5 | **Endpoint agent, last, desktop only** (Windows/macOS): local Wi-Fi/VPN/DNS/TCP view + synthetic from the user's seat; published footprint (CPU/RAM/network); privacy posture documented (no content, no URLs beyond app class unless opted) | install per device |

Identity: user · endpoint · session · site · application · path/seam, with **identity
confidence as data** (randomised MACs, NAT'd users), a subnet → site map, and the existing
`PathSource`/`MeasurementTier` provenance.

## 4. Attribution — the product
- Every degraded window is placed on the seam path the correlation engine already models:
  **red mid-path = forwarding loss → path/seam owner; red at target = terminal loss →
  application owner.** The RCA object gets the DEM evidence class (additive to the probes lane
  that already grounds).
- Per-fault-class baselines (Wi-Fi onboarding step, DNS, TLS, first byte, BFD SLA) so the
  attribution names the phase, not just the segment.
- Sub-minute detection: DEM windows are 1 min for real-time classes, 5 min for web/thick;
  alerts on experience (availability below budget for N minutes, p95 over budget, score band
  drop for a cohort) route through the product notifier with the seam owner named.

## 5. The dashboard (glossy bar — merged with the owner's vision)
One screen, dense, dark-first, animated only where motion carries meaning:
1. **Experience header:** tenant score gauge (worst-of / p95 toggle, formula on hover), users
   affected now, sites Good/Fair/Poor, apps Good/Fair/Poor, detection latency stat, evidence
   coverage (which tiers are feeding).
2. **Site × application heatmap:** cells coloured by band, sized by users; hover = components
   and the seam attribution; click = drill.
3. **Path ribbon** for the selected site/app: device → radio → LAN → egress → WAN → ISP →
   SaaS/DC → app tier as a horizontal seam strip, each segment carrying its own score, red at
   the failing seam, with forward/reverse where measured; the existing Flow Trace view opens
   underneath for hop detail.
4. **Timeline scrubber:** score over time with band shading; scrub to any minute and every panel
   re-renders to that moment; incidents and config changes as ticks.
5. **Users & endpoints:** worst users now (cohort-classified), their seat's evidence (Wi-Fi,
   VPN, DNS, calls), one-click "explain" → Iris with the evidence chain.
6. **Geo map** of sites and ISPs (blackout vs brownout), SaaS front doors as anchors.
7. Honest states everywhere: "not measured — reason", tier coverage badges, never fabricated
   zeros; perf budget for 200 sites × 50 apps.
Visual grammar borrowed: ThousandEyes path visualisation, Mist SLE bars, ZDX gauges,
Catchpoint's Internet map, Aternity's experience grades, Meraki's separate hue channel for
events vs state — restyled to Correlix's own type scale and palette.

## 6. Packaging and licensing
`FeatureDEM` (semantic entitlement); one transparent, countable unit (monitored users or sites —
decision with the owner), no expiring credits; RUM and the desktop agent are add-on units; the
Tier-0 sources are part of the core product's honesty about experience.

score maths with not-measured, routes. W2: Tier-0 sources (flow ART, SD-WAN IPFIX SLA, wireless
