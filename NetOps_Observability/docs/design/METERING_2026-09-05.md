## 1. Why this is a separate contract

Licensing needs two data models, and the owner strategy is explicit that they
must not be conflated:

```text
ENTITLEMENTS   "What is this customer ALLOWED to do?"   internal/entitlement + internal/licence
METERING       "What did this customer actually USE?"   internal/metering
```

Conflating them is how a monitoring product ends up refusing work because a
counter moved. So the separation is structural, not stylistic:

- **`internal/metering` gates nothing.** It has no admission path, no refusal,
  no ceiling and no opinion about price. Nothing in the product asks it a
  question before doing something. A metering outage costs a usage report some
  precision; it can never refuse a device, break a query or weaken isolation.
- **It reads no environment and reaches nothing it was not handed.** The
  composition root supplies a `Sampler`; the package supplies the vocabulary,
  the arithmetic, the store and the document.
- **It is removable.** Delete the `METERING` marker blocks in `main.go` and the
  package: the two Usage routes stop being registered, four metric series stop
  being emitted, and nothing else changes.

## 2. Where the numbers come from

The primary meter is counted from **configuration**, never from telemetry
activity (owner decision, 2026-09-05):

```text
counts:      a collector is enabled on this device
NEVER:       a packet arrived from this device in the last 15 minutes
```

A device counted by recent traffic drops out of the meter during the outage the
customer bought the product to diagnose, and the bill moves while the network is
down. Configuration does not do that. This is the same unit the licence ceiling
counts (owner decision C4), read from the same monitored set, so the Licence
page's bar and the usage report cannot disagree.

Every meter declares its **source**, and one of the three values is an admission:

| Source | Meaning |
|---|---|
| `configuration` | read from the platform's own configured state |
| `counter` | read from a counter the platform already keeps (in-process, or in the metrics store) |
| `not_measured` | there is no counter for this on this installation — with the **reason** recorded beside it |

**A meter with no counter is `null` with a reason. It is never a zero.** A zero
means "we counted, and it was none"; a blank means "nobody counted". A usage
report that merged them would be lying in one of the two cases. `Fold` refuses a
`not_measured` reading with no reason, and refuses to let one overwrite a real
measurement taken earlier in the day.

## 3. The meters

Scope `any` means the meter is recorded on a tenant's row (that tenant's number)
**and** on the installation row (the platform-wide total). The two are not
addends: a device assigned to no tenant is platform-owned, so it appears in the
installation total and on no tenant's row, and the tenant rows can sum to less.

### Entitlement meters — the numbers a true-up conversation uses

| Meter | Unit | Roll-up | Scope | Source in this build |
|---|---|---|---|---|
| `monitored_devices_unique` | monitored devices | union of the day's samples | any | **configuration** — the monitored set |
| `monitored_devices_peak` | monitored devices | peak | any | **configuration** — the monitored set |
| `monitored_devices_withheld` | monitored devices | peak | installation | **configuration** — devices the ceiling is holding back |
| `watched_prefixes` | watched prefixes | peak | any | **configuration** — the BGP watchlist store |
| `tenants` | tenants | peak | installation | **configuration** — the tenant register |
| `orgs` | organisations | peak | installation | **configuration** — the org register |
| `effective_retention_days_flows` | days | last | installation | **configuration** — `chschema.RetentionConfig().Flows` (the api applies this TTL itself) |
| `effective_retention_days_findings` | days | last | installation | **configuration** — `chschema.RetentionConfig().Findings` |
| `effective_retention_days_correlation` | days | last | installation | **configuration** — `chschema.CorrRetentionConfig().History` |
| `effective_retention_days_logs` | days | last | installation | **configuration** when `OPENSEARCH_LOG_RETENTION_DAYS` is in the api's environment; otherwise **not_measured**, naming the bootstrap that applies it |
| `effective_retention_days_metrics` | days | last | installation | **not_measured** — a VictoriaMetrics start-up flag (`VICTORIA_RETENTION`) the api cannot read |

### Diagnostic meters — recorded because they are useful, not because anything is charged

On-premises telemetry ingestion is **not metered for money**: "Correlix is not
paying for the customer's disks, network or compute" (strategy doc). These exist
so an operator can see what their installation costs to run, and so a future
SaaS design has evidence rather than guesses.

| Meter | Unit | Roll-up | Scope | Source in this build |
|---|---|---|---|---|
| `metric_samples_ingested` | samples | sum | installation | **counter** — `sum(increase(vm_rows_inserted_total[1h]))` |
| `metric_series_active` | series | peak | installation | **counter** — `sum(vm_cache_entries{type="storage/hour_metric_ids"})` |
| `log_accepted_records` | records | sum | installation | **counter** — the pipeline's log sinks, *after* the processors ran |
| `flow_accepted_records` | records | sum | installation | **counter** — the pipeline's flow sinks |
| `trace_accepted_spans` | records | sum | installation | **not_measured** — no distributed-tracing pipeline is configured |
| `dem_checks_run` | checks | sum | any | **counter** — `count_over_time(dem_probe_success[1h])`, which carries a tenant label |
| `hosted_ai_tokens_estimated` | tokens | peak | any | **counter** — the per-tenant daily provider budget (`ai.DailyBudget`), which resets at UTC midnight, so the day's peak is the day's total |
| `hosted_ai_tokens_input` | tokens | sum | tenant | **not_measured** — the budget keeps one combined chars/4 estimate for a spend ceiling, not separate halves |
| `hosted_ai_tokens_output` | tokens | sum | tenant | **not_measured** — same reason |
| `processor_input_records` | records | sum | installation | **counter** — records entering the pipeline (source components) |
| `processor_output_records` | records | sum | installation | **counter** — records leaving into a store (sink components) |
| `processor_output_input_ratio` | ratio | last | installation | **counter** — out ÷ in; `not_measured` when either half is missing or nothing entered (a ratio over zero input is undefined, not 0) |

Every counter above is read at sampling time; when the metrics store does not
answer, the meter is recorded as `not_measured` naming the failure, and the "the
store did not answer" and "the counter has no series" cases carry **different
sentences** — a broken dependency and a pipeline that is not running have
different fixes.

## 4. Sampling and roll-up

- **Hourly snapshot, daily roll-up.** `METERING_INTERVAL` (default `1h`). A
  per-minute sample would rewrite a row 1,440 times a day to move a number that
  changes when an operator clicks something; a daily sample would miss the peak
  entirely.
- **The first snapshot is immediate at boot**, so the staleness rule can tell
  "just started" from "stopped recording".
- Each aggregation is a property of the **meter**, declared once, so the API,
  the report and the page cannot roll up differently:
  `peak` · `unique` (union of the day's samples) · `sum` · `last`.
- **A period roll-up of a `unique` meter is the highest DAY, not a union across
  days**, and says so in its reason. The identity sets behind a closed day are
  discarded (see below), so a cross-day union is not derivable — and inventing
  one would be a fabricated number in the place a customer is most entitled to a
  true one.
- **Retention: 400 daily rows** (`metering.RetentionDays`) — thirteen months, so
  an annual true-up can look back over a full contract year plus the month it is
  being discussed in. Pruned by the recorder on every snapshot.
- **The open day keeps its identity sets; a closed day does not.** The unique
  count is the answer once a day closes, and keeping thousands of device ids per
  tenant per day for 400 days is a storage bill nobody asked for. Sealing rides
  the write that was happening anyway.

## 5. Storage

`metering_daily (tenant_id, day)` — Postgres with the `tenant_iso` FORCE-RLS
policy (migration 0046) when the platform's Postgres backend is active, and a
JSON file at `/data/api/metering.json` (`METERING_FILE`) otherwise. Both satisfy
the same `Store` interface and answer identically.

**Isolation lives in the store** (§3a rule 4). Every read takes a
`(tenant, cross)` pair and there is no unscoped "list all":

| Caller | Rows |
|---|---|
| `cross = true` | every row, including the installation row |
| `cross = false`, tenant `""` | **nothing** — default-closed |
| `cross = false`, tenant `X` | X's rows and nothing else |

The **installation row's** tenant key is the empty string. A tenant id is never
empty, so the row policy `tenant_id = current_setting('app.tenant_id')` never
matches it for a tenant-scoped read: only the `'*'` platform scope sees it. That
is the posture those meters need — how many tenants an installation has is the
provider's number, not a tenant's. `internal/metering/pg_test.go` proves it with
an unfiltered `SELECT count(*)` under a non-superuser role.

## 6. The routes

```text
GET /api/system/licence/usage?from=&to=&tenant=          the roll-up, as the page renders it
GET /api/system/licence/usage/report?from=&to=&tenant=   the same period, SIGNED, as a download
```

Both are reads, gated by `requireAdmin` at whatever scope the caller holds it —
the same gate the Licence page's read uses.

- **The scope comes from the principal, never from the request.** A tenant/org
  admin gets their own tenant; the platform owner gets every tenant plus the
  installation row.
- **`?tenant=` may only NARROW**, and only for a caller who already reads across
  tenants. A tenant-scoped caller naming any tenant but their own gets **404** —
  never a 403, which would confirm that the other tenant exists.
- A tenant's payload carries **no customer name, no licence id** and no
  per-tenant breakdown. Absent, not blanked.
- `from`/`to` are UTC days and default to the last 30. A reversed or malformed
  period is a **400**, not a quietly empty answer.
- The report download is **audited on both outcomes**.

Cross-org proof: `src/backend/metering_isolation_test.go` (own-only list,
cross-tenant selector → 404, `as_tenant` into another org ignored, owner sees
all and may narrow, and the same for the signed report).

## 7. The signed usage report

The requirement is one sentence: *the customer and Correlix must derive the same
counts independently.* Four things make that literally true:

1. **The document carries the daily rows**, not just a total, so the arithmetic
   can be redone by hand.
2. **Canonical bytes**, so two encoders produce the same signature input.
3. **A signature** whose public key travels in the document.
4. **Nothing is sent anywhere.** There is no phone-home in this package or in
   anything that calls it. The report is a file the customer downloads and
   chooses to share.

### Canonicalisation (pinned by a golden test)

`metering.CanonicalReportPayload`:

- JSON, UTF-8, **no whitespace** between tokens;
- every object's keys **sorted by byte order, at every depth**;
- **no HTML escaping** — `<`, `>` and `&` are written literally;
- numbers keep the exact literal Go's encoder produced;
- the `signature` field is **absent** from the signed bytes.

Sorted keys rather than the licence document's field-order mirror is deliberate:
a licence has one shape, but a report grows a field whenever the meter
vocabulary does, and a hand-maintained mirror would silently stop covering the
new one. Sorting is total over whatever the struct holds.

Everything outside the canonical form is free: an operator may pretty-print,
re-indent or reorder the file's keys and it still verifies.
`report_test.go:TestCanonicalPayloadIsPinned` holds the exact bytes for a fixed
document. **If that constant ever changes, the format changed — that is a new
`ReportVersion` and a migration, not an edit to a test.**

### The report key

A per-**installation** ed25519 keypair, generated at first use and stored beside
the licence at `/data/api/licence-report-key.json`, mode **0600**.

**It is not the licence signing key**, and it must never be. Correlix's licence
key lives offline on a signing host and does not exist on a customer machine —
that is the custody story in `docs/runbooks/licensing.md` and it stays true. A
usage report is produced *on* the customer's installation, so it cannot be
signed by a key that is not there. The two answer different questions: "did
Correlix issue this licence" and "did this installation produce this report".

What the signature proves: the report was produced by this installation and has
not been altered since — which is what a true-up needs, because both sides can
then compute the same numbers over the same bytes. What it does **not** prove:
that the numbers are true in some absolute sense. A customer who edits their own
installation's state changes what it honestly reports. That is not a hole to
plug with cryptography, and pretending otherwise would be the dishonest part.

Failure behaviour: a key file that exists but cannot be read is **never silently
replaced** (that would orphan every report already filed under the old
identity) — the download is refused with the reason. A key that cannot be
*stored* still signs, and the surface says the identity is not durable.

### Verifying offline

```bash
correlix-licence usage-verify <file>                 # embedded key
correlix-licence usage-verify --pubkey <base64> <file>   # confirm WHICH installation
```

Two independent checks, and the second is the one a true-up turns on:

1. the ed25519 signature over the canonical bytes;
2. the period totals, **re-derived from the daily rows in the file** and
   compared. A report whose summary does not follow from its own detail is
   refused, naming the meter that disagrees.

## 8. Metrics and alerts

| Series | Meaning |
|---|---|
| `netops_metering_snapshot_timestamp_seconds` | unix time of the last successful snapshot; **0 = none yet**, a value and not a gap |
| `netops_metering_daily_rows` | daily rows currently persisted |
| `netops_metering_snapshot_failures_total` | snapshots that did not land |
| `netops_metering_pruned_rows_total` | rows dropped by the retention sweep |

All four are emitted on every scrape, including as zeros: a series that vanishes
must mean a scrape failure, not a state change.

Rules (`src/config/rules.yaml`, group `metering`; tests in
`src/config/rules-tests/metering.test.yaml`), all **warning**, none `tier: page`
and none carrying a `layer` label — they go to the product notifier and the
warning digest, never to a phone:

- **`MeteringSnapshotStale`** — no snapshot for > 3 h, `for: 15m`. The
  `and on() (… > 0)` guard is what separates *stale* from *never*: without it
  every fresh install would fire, because `time() - 0` is ~57 years.
- **`MeteringNeverRecorded`** — the timestamp is still 0 an hour after start.
- **`MeteringSnapshotsFailing`** — ≥ 3 failures in 3 h, which staleness cannot
  see because some hours still land.

## 9. What is deliberately NOT metered on-prem, and why

- **Ingestion is not metered for money.** Bytes, samples, records and spans are
  recorded as *diagnostic* meters and labelled as such on the page and in the
  document. Correlix does not pay for the customer's disks, network or compute,
  and charging for them would be charging for someone else's costs.
- **No per-feature meters.** The strategy is explicit that seven visible billing
  meters is "commercially precise but cognitively expensive". One primary unit —
  the monitored device — with a small number of secondary meters kept for
  evidence, not for invoicing.
- **No price, anywhere.** Pricing is an order-form term. Nothing in this package,
  the licence file or the report states a rate, a window, or what an overage
  costs.
- **No phone-home, at all.** Not opt-in, not "anonymous telemetry", not a
  heartbeat. If Correlix wants a customer's numbers, the customer sends the
  signed file.
- **No user-level or per-person metering.** The unit is a device; who logged in
  is not a commercial fact.
