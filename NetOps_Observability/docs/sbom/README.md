|---|---|---|

## Why this exists next to the CI SBOM

`.github/workflows/supply-chain.yml` already emits a Trivy CycloneDX document — but only as an
ephemeral workflow artifact that expires. You cannot diff it, cite it in release notes, or hand it to
a customer asking what is in the appliance. These files are committed, so:

- a component appearing or changing version is a **reviewable line in a pull request**;
- "what shipped in `v0.9.0`" is answerable from the tag alone;
- `tests/test_sbom.py::test_committed_sbom_matches_the_current_dependency_tree` fails when a
  dependency moves and the SBOM is not regenerated.

This is the *inventory*. The Trivy scan is what resolves CVEs against it — the two are complements,
not alternatives.

## Reading the annotations

Each component carries `properties` beyond the CycloneDX basics:

| Property | Meaning |
|---|---|
| `correlix:class` | which of the five inventories it came from |
| `correlix:direct` | Go only — `true` means a direct `require`, i.e. part of the **CLAUDE.md §6 allowlist surface**. There should be exactly three. |
| `correlix:vendored` | Go only — present in `vendor/`, so it is in the offline build |
| `correlix:dev` | npm only — a build-time dependency, not shipped in the runtime image |
| `correlix:image:digest-pinned` | container images — `false` is an audit finding, not a detail |
| `correlix:origin` | container images — every `file:line(service)` the pin appears at, so a change can be applied everywhere |

## Scan scope: the TRACKED tree

Only git-tracked files are scanned. This is a correctness requirement, not a
preference: three compose overlays here are gitignored — `compose.offline-images.yml`
(generated by `install.py --offline`), `compose.lab.yml` and `docker-compose.override.yml`
(site-local) — and between them carry 25 `image:` lines that exist on a developer's machine
and in no clean clone. Including them made the committed SBOM describe one working directory,
so `scripts/sbom.py --check` passed locally and the same commit failed in CI.

Outside a git checkout (a source tarball) the scan falls back to walking the tree and prints a
WARNING saying so — a silently different scan scope is exactly the failure this guard removes.

## Known finding visible in this data

`container-images.cdx.json` shows **6 of 35** image references not digest-pinned. Four are
locally-built `netops-*` images, which have no registry digest by definition. **Two are genuine
findings:**

| File | Reference |
|---|---|
| `deployment/docker/cloud-ingest/Dockerfile` | `python:3.12-slim` |
| `deployment/docker/vm-image-builder/Dockerfile` | `ubuntu:24.04` |

(`docker-compose.flowgen.yml` and `scripts/lab/traffic-generator/Dockerfile` share the first of
those two references.) The CIS-Docker gate requires digest pins only on the four *owned*
Dockerfiles, which is how these slipped through. Note also that `scripts/lab/twin/docker/Dockerfile`
pins a **different** `python:3.12-slim` digest than `Dockerfile.correlation` — two pins of one tag
drifting apart.

> **Not a finding:** `compose.offline-images.yml` is tag-only *by design*, and cannot drift. It is
> generated by `install.py` from `docker-compose.yml`'s own digest-pinned entries at offline-install
> time, because `docker load` restores image **tags, not registry digests**; the bundle's
> `SHA256SUMS` carries integrity end-to-end instead. It is gitignored and therefore absent from this
> SBOM, which is correct — it describes a per-host generated artifact, not the shipped source.

## Determinism

Same commit + same dependencies ⇒ byte-identical output. The timestamp is the HEAD commit date (or
`SOURCE_DATE_EPOCH`), never "now", and the serial number is derived from a hash of the component set.
A committed artifact that churned on every run would be noise nobody reads — and noise nobody reads
is how a real change slips through.
