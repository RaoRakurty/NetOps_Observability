# Correlation memory A/B — does it plateau, or chase the ceiling?

Same build (`11a616e5`), same image, same 1k twin workload, same 2 replicas,
BUS_PARTITIONS=4, same backends, same host, same sequence. **Only the
correlation memory limit changed.**

| | Run A | Run B |
|---|---|---|
| limit | 827,326,464 B (789 MiB) | 1,610,612,736 B (1.5 GiB) |
| image | `sha256:05a5e9e1…` | `sha256:05a5e9e1…` (identical) |
| samples | 264 (**sampler died at 12:14 — see §7**) | 505, **sampler alive at leg end** |

---

## The answer

**Memory PLATEAUS. It does not chase the ceiling.**

| | Run A (789 MiB) | Run B (1.5 GiB) |
|---|---|---|
| peak cgroup memory | **827.7 MB = 100% of cap** | **724.2 MB = 44% of cap** |
| settled cgroup memory | 821.9 MB | **666.1 MB** |
| peak process RSS | 789.5 MB | 706.0 MB |
| peak swap | **451.9 MB** | **0.0 MB** |
| `memory.max` hits | **5,850** | **0** |
| PSI memory full_total | **36.6 s** | **0.0 s** |
| PSI memory some_total | 37.3 s | 0.1 s |

Given twice the headroom, correlation used **less** memory (724 MB vs 827 MB)
and stopped there. That is the healthy-sizing signature, not pathological
growth: at 789 MiB the process is not merely near its cap, it is *thrashing*,
and the thrash inflates its own footprint.

**The 789 MiB limit is undersized.** The measured working set peaks at ~706 MB
RSS with the window at its full 50,000 signals, which leaves ~65 MiB of headroom
at the current limit — not enough to absorb the burst, so it swaps.

## RSS vs live Python heap

| run | point | RSS | live heap | gap | gap % |
|---|---|---|---|---|---|
| A | during a stall | 789.5 M | 176.3 M | 459.1 M | 58% |
| A | settled | 553.2 M | 11.7 M | 537.0 M | **97%** |
| B | peak (window = 50,000) | 706.0 M | 170.7 M | 383.5 M | 54% |
| B | settled | 628.7 M | 7.9 M | 616.1 M | **97%** |

Two things are true at once and both matter:

* **The live working set is real and bounded** — ~170 MB of traced Python heap
  when the window is full, in both runs. That is the legitimate cost of a
  50,000-signal evidence window.
* **The resident footprint is dominated by allocator residency** — after the
  drain, live heap falls to 8–12 MB while RSS stays at 553–629 MB. The gap does
  not grow after useful work stops; it *stabilises*. It is a high-water mark,
  not a leak.

A leak would keep climbing after the workload ends. This does not: Run B settled
at 666 MB and stayed there through the 15-minute post-settlement window.

## Consumer stability — and the finding that survives more memory

| | Run A | Run B |
|---|---|---|
| stability phase | **PASS** | **FAIL** |
| `CommitFailedError` | 0 | 3 |
| `UnknownMemberIdError` | 0 | 159 |
| consumer restarts | 0 | 3 |
| worst event-loop stall | 12,703 ms | **30,989 ms** |

Run B failed stability with **zero memory pressure** — no swap, no cap hits, no
PSI. So memory pressure is not the only cause of loop stalls, and removing it
does not by itself buy stability.

Per replica: every one of Run B's events was on **replica 2** (159 / 3 / worst
30,989 ms), while replica 1 was clean (0 / 0 / worst 12,415 ms). The single
stack captured on replica 1 points at the residual cause:

```
File "/app/signals.py", line 605 in signal_id      <- uuid5
File "/app/main.py",    line 1480 in _prune_buffer
File "/app/main.py",    line 1925 in _engine_cycle_inner
```

`_prune_buffer` computes `str(WINDOW_BUFFER[0].signal_id)` — a fresh uuid5 —
for **every signal it evicts**, inline on the event loop. With a 50,000-signal
window under continuous eviction that is an unbounded synchronous loop, and it
is the same unmemoised `signal_id` that tracker 156 deliberately left
unmemoised (an instance memo costs +944 bytes per signal). This is a
NON-MEMORY stall source and is now the leading candidate for the residual
stalls.

## Backlog capacity — unchanged by memory

| | Run A | Run B |
|---|---|---|
| drain | FAIL, final lag 433,467 | FAIL, final lag 444,352 |

More memory did not improve drain at all. **Memory stability and processing
capacity are separate problems**, exactly as the separate-capacity case
predicts.

## Interpreter-level failure at the cap (Run A only)

One event dead-lettered at 12:07:16, within a minute of RSS reaching 100%:

```
SystemError: Objects/tupleobject.c:909: bad argument to internal function
```

That is a CPython *internal* error, not an application exception. Running at the
cap does not merely make correlation slow — it makes the interpreter fail. The
handler quarantine caught it and preserved a replayable payload, so the
durability contract held, but the event never became a signal. Run B produced no
such error.

Follow-up (deliberately NOT done during the A/B, since the build must not change
between legs): `keep_deadletter_payload` does not stamp a `reason`, so this
record lands in the same "(no reason field)" bucket tracker 160 fixed for the
ClickHouse batch path. The handler path needs the same treatment, and a
`SystemError` deserves its own alarm.

## §7 — evidence completeness

**Run A's post-settlement trajectory is INCOMPLETE.** Its external sampler died
silently at 12:14:20 with an empty stderr — 26 minutes before the leg ended,
through the exact window the experiment exists to measure — because a
process-group signal reached it. Run A's peak/pressure numbers stand (they were
captured before 12:14) and its post-drain figure comes from the ladder's own
memflat measurement (314 → 770 MiB, 97.5% of cap), which is independent of my
sampler.

The launcher now uses `setsid`, verifies the sampler started, and records
`sampler_survived=yes|no` at the end. Run B reports **sampler_survived=yes**, so
its trajectory is complete. A monitoring gap in the critical window is
incomplete evidence, not a clean run.

## Tracker 156 sub-gate verdicts

| sub-gate | verdict |
|---|---|
| per-event CPU starvation at normal memory | **PASS / FIXED** |
| consumer stability with memory headroom | **FAIL** — Run B had headroom and still failed (replica 2) |
| consumer stability near the memory ceiling | **PASS in Run A**, but that is the pressure-free-by-luck case; do not bank it |
| memory stability | **PASS, conditional on sizing** — a defensible plateau exists (666 MB settled, 0 swap, 0 PSI) at 1.5 GiB; it does NOT exist at 789 MiB |
| backlog capacity | **NOT YET QUALIFIED** — unchanged by memory (433k vs 444k final lag) |

## Recommended allocation

Measured need: **~706 MB peak RSS / 724 MB cgroup** with the window full.

A defensible limit is **1.0–1.25 GiB** (≈1.4–1.7× the measured peak), not the
1.5 GiB used here — that figure was a diagnostic ceiling chosen to expose growth,
and it is not evidence for itself. 789 MiB is measurably too small.

**This must not be adopted yet.** It is one workload shape on one host, and the
residual `_prune_buffer` stall is unfixed; a sizing decision taken before that
fix would be sized around a defect. The recommendation is: fix `_prune_buffer`,
re-measure the plateau, then set the limit from the re-measured peak.

## Ready for a clean 1K qualification?

**No.** Two blockers remain, neither of them memory sizing:

1. `_prune_buffer`'s per-eviction uuid5 on the event loop — a stall source that
   survives unlimited memory and produced a 30,989 ms stall past the session
   timeout.
2. Backlog drain, which no amount of memory improved.
